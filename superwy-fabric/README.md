# SuperWY Fabric 仓库客户端

## /superwy web 一键打开管理网页（0.6.7，玩家端 0.6.2 无需更新）

游戏内输入 `/superwy web`：生成本机管理地址 `http://127.0.0.1:端口/#token=…`，复制到剪贴板，并在聊天栏显示可点击的链接。浏览器打开即自动登录，不用再手动粘贴令牌。令牌放在 `#` 后面，浏览器不会把它发给服务器，页面读取后立即从地址栏删除。链接里含管理令牌，只在本机使用，不要发给别人。已经打开的网页里粘贴这个链接也会直接登录。

## 网页缺货对比（0.6.6，玩家端 0.6.2 无需更新）

网页新增“缺货对比”页（管理员）。在 Litematica 材料列表里导出 **JSON** 格式（`config/litematica/material_list_*.json`）并上传，点“重新扫描全部仓库后对比”：机器人重新扫描当前世界所有未单独停止的仓库区域，扫完后用每种材料的 Missing（投影里还缺的数量）对比仓库库存，只列出仓库不够的物品和还差多少个，可一键复制。也可以“直接用当前库存对比”跳过扫描。物品名按内置的中文名表（`web/names.csv`）显示，表里没有的显示物品 ID。CSV/TXT 导出用的是中文名，部分新物品无法对应回物品 ID，所以只接受 JSON。接口：`POST /api/v1/admin/shortage`，请求体 `{"items":[{"itemId":"minecraft:stone","count":64}]}`，最多 4096 行。

## 装盒一次打开依次放入；缓存刷新不再打断任务（0.6.5，玩家端 0.6.2 无需更新）

- **装盒更快**：以前每装一叠都要打开盒子、放入、关闭，再用两次查询核对，然后重新打开。现在打开盒子一次，先算好这一轮所有散货放在哪一格（同物品先补满盒里没满的那一叠），依次放进去，关上后用一次扫描同时核对盒子和背包。盒子装满时换下一个盒子继续。扫描结果和计划不一致时，按盒子和背包的实际内容记账并继续，不再结束任务。
- **缓存刷新不再打断任务**：机器人每次用完一个箱子（取货、取空盒、归还借出的潜影盒、存余物）都会顺手刷新这个箱子的库存缓存。以前这次查询超时或排队失败会让整个任务失败；现在只记日志，任务继续。玩家取消仍然立即生效。

## 装盒修复：装满一盒才交付（0.6.4，玩家端 0.6.2 无需更新）

以前背包里有其他任务留下的物品、空格很少时，每轮只能取一两格，装进盒子后又因为“没有空格”直接召唤假人，把只装了一个物品的盒子交出去；下一轮再拿新盒子，反复召唤假人。现在：

- 手上已有没装满的盒子时，不再为新盒子预留空格，每轮能多取一格。
- 所有装盒订单（普通批量、投影、调度任务块）都把没装满的盒子留在身上继续装，装满或整单取完才召唤假人；携盒达到上限时只交出装满的盒子。
- 空格不够时，先把背包主物品栏里不属于本单的物品（快捷栏、装备、副手除外）存进余物存放箱，再继续取货；余物箱满或关闭了“定期背包存箱”时，用剩下的空格继续，仍然装满一盒才交付。

## 不再因“需要核对”结束任务（0.6.3，玩家端 0.6.2 无需更新）

以前取货途中箱子内容被改动（多台机器人同时开同一个箱子、补货机换盒）时，机器人会拿整个背包和预期比对；只要快捷栏里有一件数据读法不同的物品（附魔工具、地图、书等），就判定“存在需要核对的物品记录”，整个任务块失败，表现为一件没取、全部“未取到”。现在：

- 核对只看这次搬运会碰到的格子（目标货物格、借出的潜影盒格），快捷栏和其他物品不再参与比对。
- 实际到手数量和预期不同（例如被另一台机器人拿走一部分）时，机器人用 NBT 查询扫描自己的背包，按真实数量更新记录后继续；少了的部分稍后重新去取。
- 打包、交付前也先扫描背包核对；对不上时按扫描结果更正并重试，每单最多 3 次。
- 超级调度模式下，任务块因机器人自身问题失败时，没交付的部分会重新派出（每种物品最多 2 次），不再直接算作缺货；真正缺货的物品不重试。

## 缺货不中断，结束时汇总（0.6.2）

所有订单（单项、批量、投影、超级调度任务块）遇到缺货都不再停止：缺货的物品跳过，其余继续取货、交付，直到整个任务做完。开始前即使缓存里查不到某物品也照常开始。任务结束后在公屏统一说明一次，同一物品多行合并，超过聊天长度自动分条：

- `完全缺货：stone×64、glass×10`（一个都没交付）
- `数量不足：dirt 缺60（已交付40）`
- `未取到：xxx×n（原因）`（因路径、界面等其他原因跳过的物品）

缺货时不再逐项刷屏；其他原因的跳过仍会即时提示。超级调度模式下由调度机器人在整单结束后汇总播报。

## 调度网页、库存预查与内存（0.6.1，需要玩家取货端 0.6.1）

- **超级调度网页**：控制台新增“超级调度”页，每 3 秒自动刷新。
  - 机器人表：在线/离线、是否可接单、正在做什么、当前任务块进度、位置、空槽、版本；离线机器人可“立即改派”（跳过 2 分钟等待）或“移除记录”。
  - 任务管理：每个任务的类型、状态、前方任务数、机器人数、已交付/总数、缺货数、未派出数量；可“置顶”或“取消”。
  - 本机设置：调度机器人名、离线判定、改派等待、任务块大小。
  - 调试：最近 200 条调度事件、下载调度状态 JSON、查看/清除收货假人锁、本机任务块。
  - 在任何一台机器人的网页上都能看和管理，操作会签名转发给调度机器人执行。
- **库存预查**：新增 `POST /api/v1/stock`，按机器人缓存返回每种物品的需要、库存和缺少数量（同物品多行合并）。超级调度模式下由调度机器人回答。
- **签名密钥**：机器人之间的签名密钥仍由 FRP 凭证派生，重新打包不变，不同打包版本的 private jar 可以互通。
- **内存**：定期存箱的计数改为在数据库里统计，不再每单加载全部历史订单；网页状态接口只读最近 10 条历史；任务块结束后缓存最终进度，不再每秒读数据库；10 分钟不上报的机器人记录、一天没回来的任务块、调度事件日志都会自动清理；机器人之间的 HTTP 响应最多 1 MB。

## 超级调度模式（0.6.0，需要玩家取货端 0.6.0）

多台机器人同时在线时使用，默认关闭。每台机器人执行 `/superwy mesh on`（或网页“接入”页的“超级调度模式”卡片）开启，`/superwy mesh` 查看状态，`/superwy mesh off` 关闭（有未完成的任务块时拒绝关闭）。所有机器人都要用主人的 `-private.jar`（任一版本均可）：机器人之间的签名密钥由其中内置的 FRP 凭证派生，重新打包不会变；普通 jar 无法开启。

- **角色**：名为 `mesh.authorityName`（默认 `tiantian996`）的机器人是调度机器人，负责排队、派活，自己也参与取货；其他机器人是工人。
- **自动连接**：工人看服务器玩家列表判断调度机器人是否在线，用签名私聊 `swmesh1 hello/welcome` 取得它的 FRP 地址，之后每秒通过签名 HTTP（`/api/v1/mesh/heartbeat`）上报状态、领取任务。私聊只用于这次握手。
- **调度规则**：单项取货优先，派给手上没有任务块的空闲机器人；批量单整单排队，前一单全部派出后才开始下一单；批量按需切块（散装每块最多 25 格，装盒单每块 2 盒），先做完的机器人领下一块，单项取货在块边界插队。玩家看到的“前方还有 N 个任务”：单项按排在前面的单项计，批量按排在前面的批量计。
- **掉线**：机器人停止上报 15 秒视为离线；2 分钟内回来接着做原来的任务块（继承身上已取的货和盒子）；超过 2 分钟，未交付部分改派其他机器人，它回来后只交付身上已有的货（玩家可能多收到一些）。交付过程中掉线、身上货物对不上时不续做，未交付部分交给其他机器人，订单标记需要核对。
- **共享资源**：同名收货假人（含 `_1`、`_2`）同一时间只允许一台机器人召唤；选货源时避开其他机器人正在开的箱子；空盒补充箱、存箱箱子被占用时最多等 30 秒。
- **玩家订单**：玩家连接任意一台机器人均可（`/superwy connect` 生成的连接指令不变），工人把订单、查询、取消转发给调度机器人。玩家端没开超级调度模式时提交会被拒绝（`MESH_MODE_REQUIRED`），提示执行 `/swrequest mesh on`。缺货和“搞定了，我歇逼了”由调度机器人统一在公屏播报，工人不说话。
- 配置项（`config/superwy/config.json` 的 `mesh`）：`enabled`、`authorityName`、`offlineAfterSeconds=15`、`reassignAfterSeconds=120`、`chunkSlots=25`、`parcelChunkBoxes=2`。

**私聊下单已停用**：`swget1`、`swbatch1` 一律拒绝（`WHISPER_ORDERS_DISABLED`）并私聊提示玩家更新取货端。玩家订单只走 HTTP；HTTP 新增 `options.batch` / `options.projectionParcels`，按批量规则执行（缺货逐项跳过、超过 25 格打包、投影单装盒）。

Minecraft Java 26.1.2 / Fabric，版本 0.6.7。客户端 mod 自带 Web 控制台、SQLite 库存索引和按清单执行的仓库订单。

## 圈投影取货打包交付（0.5.6）

配合玩家取货端 0.5.0 的“机器人取货”按钮。私聊批量会话 `begin` 带 `parcels` 标记时，订单无论大小都使用潜影盒交付，并按清单顺序装盒：同物品先补满盒内未满的堆叠，再占新格，满 27 格换下一盒。携盒达到上限或空槽不足需要中途交付时，未装满的当前盒子留在机器人身上继续装，所以除最后一盒外每盒都是满的，与取货端的预估一致。清单中的潜影盒物品在其他材料装盒后散装交付。收货假人装不下时依次使用 `收货名_1`、`收货名_2`。缺货跳过、部分交付、取消、超时和核对规则不变。不带标记的普通单项、批量和 HTTP 订单行为不变。需要服务端 QuickShulker Multi 和空盒补充点（与 0.5.0 打包相同）。

## 自动补货机换盒重试（0.5.5）

取货时容器被红石补货机替换、界面关闭或布局变化，会先安全关窗、等待 1 秒，核实服务端背包后重新打开同一坐标，每次取货步骤最多重试 3 次。已经拿到的材料按实际数量计入，不重复取货；光标仍有物品或数量无法核实的情况保留现场并停止。

库存缓存只负责定位候选容器。每次打开后均按当前菜单查找目标物品；箱内潜影盒位置、内容或盒内槽位变化时，也按这次实际打开的布局取货。源盒归还时优先使用仍空着的原槽，原槽被补货占用时改用同一容器当前允许放入的空槽，并重开核实归还结果。玩家取货端无需更新。

## 内存管理（0.5.4）

终态订单完整保存在 SQLite，内存仅保留未结束订单。控制台与取货端队列轮询只读取最近最多 10 条历史，订单详情及幂等重放仍可查询旧订单。启动时逐条读取库存，并分批迁移旧订单序号，避免同时保留全部库存 JSON 和历史订单对象。

Servux 解码最多排队 32 个分片，每个分片仍受大小限制；积压超限、解码失败、超时、断线和关闭时丢弃待解码数据并释放分片缓冲。取消中的响应仍按协议排空或在 15 秒截止时间内终止，避免旧响应被当成新请求。无需定时强制 GC。

## 取货前自动关闭容器界面（0.5.3）

每个订单从 FIFO 队列开始执行时，先检查当前鼠标光标和容器界面。光标为空时自动关闭已打开的箱子、木桶、潜影盒、GCA 假人背包或玩家背包界面，确认关闭后再校验库存并取货；无需因界面未关闭而手动重新下单。普通单项、HTTP/Web 和批量订单使用同一检查。

等待中的新订单只入队，不关闭正在执行订单的取放界面。若光标仍携带物品，保留光标和界面并以 `CURSOR_NOT_EMPTY` 停止，避免关窗导致物品意外移动或掉落；处理好光标后再下单。取消、超时、源盒核对及交付核对规则保持不变。

## 每 50 轮将背包余物存箱（0.5.2）

累计完成交付 50 个订单后，打开 `80,50,-23` 的箱子，将主背包索引 9–35 的余物存入箱内，合并同物品堆叠；快捷栏 0–8、装备和副手保持原样。普通或批量订单各算一轮，部分交付也计数，取消、完全无货和交付中断不计数。计数和清理检查点保存在订单记录中，重启保留；升级前历史订单不追溯计入。

前 49 轮不清理，第 50 轮交付并核实假人下线后执行；清空核实成功后重新累计。箱子已满或打不开时保留余物，公屏单独提示“本轮已完成交付；背包存箱清理失败：原因，余物已保留”，订单仍保留实际交付成功状态及 `cleanupErrorCode`。周期保持到期，恢复箱子空间后下一次完成交付重试。取物或存箱动作无法核实时保留现场供核对。

旧配置首次加载本版时，将原投放入口自动迁移至 `80,50,-23`；网页“取盒与定期背包存箱”可以修改清理箱坐标，兼容配置/API 字段名仍为 `returnEntry`。机器人使用开箱交互距离寻路，无需站在箱子上或紧贴入口。`cleanupMainInventory=false` 可关闭定期清理。本次只需更新机器人端。

## 普通订单缺货时交付已取物品（0.5.1）

普通订单取货过程中耗尽货源后，记录该行未取数量，继续处理后续行，最后交付已核实取到的物品。例如要求石头 64 个、实际取到 54 个，会将 54 个存入收货假人并核实下线，订单记为 `partial_stored_offline`，公屏普通聊天发送 `minecraft:stone 缺货10个，已交付54个`。批量订单也在结束后按缺货物品 ID 汇总实际交付数量，每种物品一次；重复行合并计数。

普通订单开始前若某行完全没有候选货源，仍以 `OUT_OF_STOCK` 结束，公告对应数量及已交付 0 个。`allowPartial` 保留兼容，不控制上述行为。物品、光标、源盒或交付无法核实时仍停止并保留现场，不将已取数量冒充已交付数量。本次只需更新机器人端。

## 超背包打包与任务后清理（机器人 0.5.0 / 收货端 0.4.0）

清单预计占槽超过 25 格自动启用打包。第一轮最多取 25 格，后续每轮最多 24 格，并按当前空槽预留两个工作槽；通过服务端 QuickShulker Multi 将材料装入潜影盒，填满 27 格后再用下一盒。携带盒数达到 25 时立即交付并继续剩余清单；接收假人满时依次使用 `收货名_1`、`收货名_2`，超出 16 字符时缩短基础名称。请求物品本身是潜影盒时采用散装分批交付，避免盒中装盒。

网页“仓库区域 → 打包与全物品入口”可修改入口（默认 `100,49,0`）、空盒箱（默认 `129,53,-21`）、每轮占槽上限及携盒上限（均为 1–25）。原有当前站点的 `boxSupply` 恢复使用；网页保存会同步站点与默认坐标。也可对准目标用 `/superwy station box` 或 `/superwy station return` 保存。Carpet Org Addition 64 堆叠空盒每次只领取 1 个，不整组拿走。

任务完成交付后，走到全物品入口旁，将主背包索引 9–35 的余物逐格投向入口，再以服务端 NBT 核对已清空；快捷栏、装备、副手保持原样。入口需有可通行邻接站位和接收掉落物的设施。配置 `cleanupMainInventory=false` 可关闭清理。取消、断线或物品转移未核实时保留现场物品，供人工核对。

清单最多 128 行、合计 100 万件，不再按双方空槽减 5 限制整单。先用队列键开始草稿，再按取货键打开数量窗，可输入 1–1000000。右下角显示取货件数、携盒数及任务排队进度。普通任务执行上限 500 秒，打包任务默认 24 小时，均受订单自身有效期约束。缺货与可核实的项目异常仍逐项跳过，最终交付已取材料并发送 `搞定了，我歇逼了`。


## 单项与批量任务混合排队（机器人 0.4.19 / 收货端 0.3.7）

机器人正在批量取货时，可继续提交单项、批量及 HTTP/Web 任务。所有任务按机器人成功受理的顺序共用同一条 FIFO 队列，当前任务继续执行。每个凭据仍最多 5 个未结束任务，全局上限 100 个；编辑草稿本身不占任务队列，确认提交成功后才排队。

提交后右下角会显示每张任务，例如 `队列中，前方还有 3 个任务`。前方数量包含正在执行的一张任务；前面的任务完成、取消或失败后自动更新。私聊单项和批量通过机器人私聊回传队列变化（约每秒检测一次，只发送变化），HTTP 单项按原凭据每 3 秒查询自己的订单。同一玩家可以继续编辑新批量，旧任务的队列和取货进度分别保留，完成提示停留约 15 秒。

0.5.0 起，草稿直接返回最多 128 行的清单上限，超背包材料由打包与分批交付处理。等待中的草稿不会召唤、移除正在使用的收货假人，也不暂停当前取货。仍保留批量缺货与界面异常逐项跳过和原版按键设置。

两端都需更新至上述版本。自用机器人 jar 保留原有 FRP 预设。

## 批量异常跳过与部分交付（机器人 0.4.18 / 收货端 0.3.5）

批量清单按行处理。缺货（包括只取到部分数量）、来源或源盒变化、容器界面关闭/切换、开箱超时等项目异常会显示 `物品ID 取货错误：原因；已跳过，继续下一项`，记录该行的 `skipped`、`errorCode` 和未取数量 `shortfall`，然后继续下一项。已经核实取到的材料保留，处理完全部项目后统一召唤快递假人、存放并下线；部分交付为 `partial_stored_offline`，公屏仍发送 `搞定了，我歇逼了`。全部无货时不召唤空快递，收货端显示“清单已处理完，均未取得材料”。0.5.1 起普通订单取货过程中缺货也交付已取物品，见上文。

右下角进度改为“已处理 / 总项数”，跳过的项目计入已处理数，同时显示跳过数量和 `[跳过]` 标记；完成时区分完整交付、部分交付及全部未取到材料。需要双方同时更新以识别新增跳过消息和结束状态。

“容器界面已变化”（MENU_DESYNC）指点击前保存的界面 ID 与当前界面 ID 不一致，不表示箱子内容必然变化。界面被关闭、切换或服务端重开界面均可触发；仅凭提示无法判断具体诱因。点击中途发生变化时先关闭空光标界面，通过服务端实体 NBT 核对取物前后的背包，核实已取数量，归还借出的源盒并刷新来源缓存，再继续下一项，避免同箱后续材料被错误视为缺货。光标仍有残留、背包变化无法核实、源盒无法安全归还、取消/断线/超时或交付不确定时仍停止并保留货物待核对，不自动重新取一份。

## 批量取货与自定义快捷键（机器人 0.4.17 / 收货端 0.3.4）

收货端 `/swrequest config` 新增“取货 / 确认 / 队列”三个按键按钮。点击按钮后按键盘键或鼠标键完成绑定，Esc 取消绑定；三个键不能重复，保存后重启保留。默认：鼠标中键取货、Enter 确认、`\ |`（Enter 上方）加入队列。主 Enter 默认也兼容小键盘 Enter。

对准投影直接按队列键，会将默认数量的材料加入批量清单；也可先按取货键编辑数量，再按队列键加入。已有草稿时数量窗允许 1–1000000。首次加入通过 `/tell` 获取清单上限，不召唤收货假人。清单在右下角显示，最多 128 行、合计 100 万件，预计超过 25 格自动打包。

选好材料后按确认键统一提交，数量窗已关闭时依然有效；若数量窗仍打开，当前材料一并入队。没有数量窗时按 Esc 放弃草稿；编辑约两分钟超时。右下角显示已处理行数（含跳过项），打包时另显示已取件数与携盒数。达到携盒上限即原地交付，再继续清单；全部处理完后交付剩余物品并核对下线，成功后公屏发送 `搞定了，我歇逼了`。

草稿编辑和批量执行期间允许新任务入队，按上文统一 FIFO 处理。清单采用有序短私聊分包发送，不受单条清单长度限制，每张清单只生成一个任务；请求失败不自动重发。

批量功能在 HTTP 设置下也使用同服私聊，需要填写机器人名并开启机器人私聊接单；普通单项取货继续使用原发送方式。双方必须更新到上述版本，旧版仍可进行普通单项取货。


## 召唤失败后清除并重试一次（0.4.15）

需要快递假人时，若首次召唤未成功，无论本地玩家列表是否显示其在线，均主动执行一次 `/player <收货名> kill`。短暂等待服务器处理并检查其离线后，在机器人当前位置重新召唤一次；成功即继续原有 GCA 存放与核对流程。第二次召唤仍失败才结束本单并保留已取货物待核对，不循环重试。取消、暂停或超时会停止清除及重试的后续操作。

## 在线快递假人重召唤与队列进度（0.4.14）

交付前若指定快递假人已在线，先执行 `/player <收货名> kill`，等待玩家列表和本地实体确认离线，再在机器人当前位置重新召唤，继续原有 GCA 背包存放、核对与下线流程。清除超时会停止本单，不继续召唤或放物；没有在线假人时直接召唤。

当前世界、维度、仓库的未完成订单（含正在处理的一单）超过 3 个时启用公屏进度提示。此后每单结束（包括执行失败或执行中取消），在订单终态保存后通过普通聊天发送 `还有N个订单在队列`，数量仅包含剩余排队订单；队列清空时改发 `都取完了，我歇逼了` 并重置。处理中新增订单也参与触发；下一批不超过 3 单时不播报。

## 所有取货失败提示使用普通聊天（0.4.13）

修复组件版本冲突（`AMBIGUOUS_ITEM`）等失败仍通过 `/say` 公告的问题。缺货、组件冲突、超时及其他取货失败统一使用普通聊天发送，例如 `minecraft:white_shulker_box 取货失败：该物品存在多个不同组件版本，请指定准确版本`。

## Servux 每十分钟定时扫描（0.4.12）

选择 Servux 时，各启用且未单独停止的区域在上一轮扫描完成 **10 分钟（600 秒）** 后启动下一轮；现有区域无需重新保存。重启按持久完成时间计算，切回 F3 后恢复区域原有间隔。手动开始仍可立即扫描，停止区域和全局关闭仍有效。网页的区域间隔及下次扫描时间显示实际协议对应的设置。

## 大库存性能优化与普通聊天缺货提示（0.4.11）

- 移除游戏主线程每秒全量解析/汇总库存的任务。库存 HTTP 接口仅在实际访问时由 HTTP 工作线程计算；Web 概览仍使用轻量状态。
- 本地库存建立按物品和区块的索引，单个容器失效时直接按键更新，取货候选查询在独立后台线程执行。空闲时只检查待处理订单，不再每个 tick 反序列化全部历史订单。索引替代常驻的整库快照 JSON，避免同时保留两份完整表示。
- F3 回复的物品组件、嵌套潜影盒内容及散列转换移到 `superwy-scan-decode`；Servux 的大回复分片重组/NBT 解码移到 `superwy-servux-decode`，区块库存转换也在后台执行。后台只读取预先捕获的注册表和独立数据，世界读取、发包、寻路、点击与扫描断点推进仍在游戏线程。
- 单个扫描操作仍按顺序等待读取和持久保存，取货优先，避免同时堆积大量查询。取消、停止区域、切协议或断线后，后台迟到结果不能覆盖库存；扫描断点保留。
- 扫描黄框仅显示 128 格内最近的最多 128 个容器，HUD 保留最近 6 个坐标，每 250 毫秒刷新一次选择结果，不再每帧全队列排序或绘制全部黄框。完整待扫队列及数量不裁剪，仍可分页查看。
- **缺货使用普通聊天发送**，例如 `minecraft:lever 缺货`，不调用 `/say`。0.4.13 起，其他取货失败也统一使用普通聊天。

保留原数据库、区域、协议选择和跨箱补货逻辑，无需删除缓存或重新扫描才能启用优化。实际 FPS 与服务器、世界渲染和其他 mod 有关，本地 CPU 测试不能代替用户服务器上的帧率实测。

## 跨区域候选货源与逐箱补货（0.4.10）

取货会汇总当前世界、维度中**所有启用区域**里缓存含目标物品的仓储容器，两个仓库区域均参与选择，无需先重新扫描全仓。按原货源优先级逐个开箱核对，数量不足时继续从其他箱子补齐同一行需求。

缓存位置的容器已消失时删除该失效快照，继续尝试其他候选；容器存在但目标物品或源潜影盒已变化时，关闭界面、刷新该容器库存，再选择剩余候选。本单记住已确认无效的来源，避免反复访问同一空箱；这些排除记录在下一单清空。刷新后出现新的源潜影盒内容时，可使用新的来源记录。

缓存数量低于需求但仍有候选时，也会现场核对并尝试取齐。0.5.1 起取货过程中候选耗尽时记录缺货，交付已取物品并公告实际数量；开始前完全没有候选货源的普通订单仍以 `OUT_OF_STOCK` 结束。不会等待后台扫描或补货。未被索引记录的容器仍需通过扫描发现。

候选切换只处理开箱前确认容器消失，以及尚未借盒/转移时发现来源变化。转移结果未确认、源潜影盒未归还、光标异常、取消、掉线和超时仍停止本单，避免重复取物；组件匹配规则保持不变。

## 仓储容器与实验性 Servux 扫描（0.4.9）

扫描仅包含**潜影盒（含所有颜色）、箱子（含陷阱箱）和木桶**。漏斗、熔炉、投掷器、陶罐等不再进入扫描队列；旧缓存中这些容器也不再参与库存统计或取货。升级后恢复断点时会清理已识别的非仓储容器。

默认仍使用 **F3 逐容器 NBT 查询**。可在游戏手动切换：

```text
/superwy scan protocol
/superwy scan protocol servux
/superwy scan protocol f3
```

第一条查看当前协议，后两条切换并保存设置，重启保留。扫描过程中切换会中止当前读取并保留待扫位置。Web 概览显示当前协议及中文错误。切换只作用于后台扫描，取货时的容器复核、玩家/假人物品栏核对仍使用原有查询。

Servux 模式实验性适配 **Servux 0.10.x 的 litematics 协议 v1**，以 0.10.4 发行包验证编解码和分片。按区块及选区高度批量读取，再以同一数据库事务写入库存和断点，可减少密集仓库的逐箱往返和逐箱落盘；实际速度仍取决于区块加载、网络和服务端处理，尚未在用户远程服务器测量。

服务端需安装对应 Servux，启用 `litematic_data` 提供器并允许当前玩家读取；区块需已加载。客户端无需安装 Servux。已验证无 Litematica，以及 Litematica 0.27.9 / MaLiLib 0.28.8、Litematica 0.27.14 / MaLiLib 0.28.12 的通道共存。扫描期间避免同时使用 Litematica 的 Servux 批量保存任务：该协议的批量回复没有可独立关联的请求编号。

Servux 原始接口返回区块高度范围内的方块实体，因此与仓储容器共处同一区块的漏斗等仍可能出现在网络回复中，客户端会过滤；仅含排除容器的区块不会发出批量请求。没有修改服务端返回范围。

握手超时 4 秒、批量请求超时 15 秒；回复限制为 32 MiB 原始数据、128 MiB NBT 内存计量。协议不可用或整批异常时暂停扫描并保留队列及历史库存，不自动切换协议；可执行 `f3` 切回继续。超时或分片损坏后若要继续 Servux，需要重新连接；普通握手问题修复后可重新开始该区域。单个容器缺失或 NBT 异常会保留旧库存并标为未完整读取。

## 仓库预设、FRP 与一条指令连接（0.4.8）

预设从现有运行实例只读导出，绑定 `bbbb.icu#default`、`minecraft:the_end`：

| 区域 | 第一点 | 第二点 |
| --- | --- | --- |
| bh | 78,49,-89 | 117,53,-6 |
| warehouse | 147,42,-74 | 173,61,91 |

首次进入匹配服务器时只补充缺少的区域，刷新周期每小时。新导入区域初始停止扫描，在网页分别开始；已有坐标、停止状态、库存和扫描断点不覆盖。导入记录持久保存，手动删除后不反复重建；其他服务器不导入。

本机 Web 默认 `autoPort=true`，由操作系统原子分配空闲端口；固定配置端口冲突也自动回退到空闲端口。游戏 `/superwy` 显示实际地址。FRP 目标预设为 `frp.example.com:17000`，使用内置 Windows x64 frpc 0.71.1，转发至本机 Web；首次公网端口从 20000–59999 随机选择；注册成功后将端口立即写入配置 `frp.lastRemotePort`，停止、重启游戏或重新启用 FRP 都优先复用。端口被占用时才随机换号，新端口注册成功后替换持久记录，最多 12 次；失败不会覆盖上次成功端口。保存失败会关闭本次隧道并提示中文错误。此设置记住公网端口，本机 Web 仍自动分配空闲端口。认证、服务端端口限制等错误显示中文；停止/退出只结束 Mod 自己启动的 frpc，不更改桌面配置或外部 frpc。

安装机器人端时二选一：

- `superwy-fabric-0.4.19-private.jar`：自用预配置版，保留原自用版 FRP 预设，首次加载写入本机配置并自动连接。此 jar 带所有者认证，不作为玩家取货端分发。
- `superwy-fabric-0.4.19.jar`：普通版，不含认证，需在 `config/superwy/config.json` 的 `frp.authToken` 填写自己的凭证，然后启动 FRP。

命令：`/superwy frp` 查看状态；`/superwy frp start` 启动/重试并保存启用状态；`/superwy frp stop` 停止且下次不自动启动。网页“连接与接口”提供相同控制、实际本机/公网地址和“生成并复制连接指令”。对外 Host 自动加入允许名单，HTTP 接口仍需 Bearer 身份验证。

FRP 就绪后，机器人输入 `/superwy connect`，无需填写收货名，自动复制 `/swrequest connect swc2.…`。玩家安装取货端 **0.3.3**，在游戏中粘贴执行，弹窗填写收货假人名（默认 `sf`），点击“保存连接”才保存地址、独立玩家凭证和收货名，切换 HTTP；不会自动下单。Esc/取消或无效名称不会覆盖原连接。之后用 `/swrequest config` 或 `/swrequest recipient MyCargo` 修改收货名；也可再次执行新连接指令重新配置。`/swrequest connect` 无参数可打开设置。

连接指令不包含管理员令牌或 FRP 认证。每次生成创建独立普通凭证，允许取货端自由选择合法收货名，订单读取/取消仍限定于该凭证自己的订单，无管理员权限。建议给每位玩家分别生成。旧 `swc1` 指令仍可导入，但旧凭证仍保留原有收货名限制，需重新生成 `swc2` 才能自由修改。指令长度不超过原版 256 字符。正常重启保持公网地址；若端口冲突换号或修改 FRP 主机，请重新生成连接指令，旧订单不会自动重发。

管理员 HTTP：`GET /api/v1/admin/network`、`POST /api/v1/admin/frp/start`、`POST /api/v1/admin/frp/stop`、`POST /api/v1/admin/connect`（请求体 `{}`，收货名由取货端填写）。状态接口不返回凭证，生成接口仅管理员可用。`frp` 配置可修改端口范围、重试次数和启动超时；无需另行安装 FRP。

## 大容量容器扫描断线修复（0.4.6）

修复开始扫描时出现 `Failed to decode packet 'clientbound/minecraft:tag_query'` 的问题。大量嵌套潜影盒和物品组件可能超过原版 2 MiB 的 NBT 内存计量预算，导致回复在进入扫描逻辑前就解码失败、断开连接。内存计量与网络包压缩后的大小不同。

仅对当前网络连接中机器人自己发出的 NBT 查询，将内存计量预算调整为 16 MiB，NBT 原始字节仍限制为 2 MiB，并保留原版嵌套深度限制。超过预算或格式异常的回复会记录中文原因并跳过容器，保留历史物品记录并标为未完整扫描，不会当成空箱覆盖。订单查询遇到同类异常会正常失败并释放队列。

暂停、取消或超时的查询保留最多 60 秒的归属记录，迟到回复直接丢弃；断线清空记录。其他连接、其他模组或原版自己的查询继续使用原版限制。本修复不改变服务器包大小限制，也不能修复在其他包类型或更早网络分帧阶段发生的断线。

另修复取货寻路的距离边界：容器目标为脚下方块中心与玩家实际位置的偏移保留接近余量；行走时不在首次触及交互距离边缘就取消路径，需落地并进入带余量的距离，停稳后再次检查实际命中点。避免紧邻其他箱子或超时后的下一单在距离边缘提前停止。

## 开箱寻路与中文提示（0.4.5）

机器人取货不需要设置工作点或交付平台。旧 `NO_INTERACTION_STAND` 指的是自动寻找开箱位置失败，并非缺少 `/superwy station` 配置。旧逻辑只枚举已加载区块中的整格空位，服务端拒绝远距离交互后还要求可见射线，容易排除半砖地面、头顶遮挡容器或未加载缓存目标。

现改为 Baritone 的容器交互距离目标：先在 10 格内直接发送目标坐标的交互包；需要靠近时，让 Baritone 从实际可走路径中寻找进入交互距离的位置，不预先枚举固定站位、不要求准星视线。服务器拒绝第一次远距离交互时，按服务器同步的交互距离再靠近一次，仍使用坐标包开箱。实际加载状态由客户端区块缓存判断；未加载缓存目标会先寻路，不误报为容器已消失。最终仍以服务器实际打开的菜单为准，箱盖被阻挡或权限拒绝会如实失败。

游戏普通聊天公告、网页原因栏、扫描失败说明和 HTTP `error.message` 统一中文，例如“收货假人物品栏已满”“服务器未打开容器，请检查距离、箱盖阻挡或开箱权限”。订单详情与摘要增加 `errorMessage`，执行能力增加 `blockingMessages`。程序协议的 `error.code`、订单 `errorCode` 等稳定代码保留，便于其他 Mod/脚本继续识别；旧历史错误也按同一字典显示中文。

## 精简 Web 与历史订单（0.4.4）

Web 移除库存表、容器内容及嵌套树，不再请求 `/inventory`，也不再下载完整 `/admin/status`。改用 `/admin/dashboard`，只返回区域、扫描计数和订单摘要；容器坐标列表不随概览发送，失败详情最多 8 条。单个订单的完整信息在点击“详情”时才读取。

列表自动保留全部进行中/排队订单，以及最近 **10 条已结束订单**，超过的历史记录自动移出列表。旧浏览器订单 ID 集合会清除；每 5 秒刷新一次，页面隐藏时暂停刷新。普通玩家也直接使用队列摘要，不再逐个拉取每条订单。库存缓存、物品查询接口、订单审计和幂等记录仍保存在服务端。

## 多区域独立扫描控制（0.4.4）

Web 的“仓库区域”中，每个区域提供“开始 / 继续”“停止此区域”及独立进度。多个运行区域按单个区块/容器步骤轮流推进，B 区不必等待 A 区整轮结束。一个机器人只有一套移动控制，同一时刻的寻路和容器读取仍串行；取货任务优先于扫描。

游戏命令：

```text
/superwy scan start warehouse_a
/superwy scan stop warehouse_a
```

开始恢复该区域上次未完成的位置；完成过的区域则启动新一轮。停止立即中止该区域正在执行的扫描寻路/查询，保存断点，不作为扫描失败、不增加跳过记录。其他区域和订单继续执行。区域的 `scanPaused=true` 保存在数据库，重启、定时扫描、全局 `/superwy scan on` 和无参数“启动未停止区域”均不会擅自恢复它；必须单独开始该区域。区域仍保持 `enabled=true`，历史库存继续参与取货。

接口：`POST /api/v1/admin/scan/start` 和 `POST /api/v1/admin/scan/stop`，请求体 `{"regionId":"warehouse_a"}`。旧 `POST /admin/scan` 带 regionId 也改为直接启动/继续，返回 `started=true`，不再返回 queued。`GET /admin/status` 新增 `scanRegions`，包含各区域状态、已读数、剩余坐标和停止标记。停止响应在配置及断点持久保存后返回。

## 箱内潜影盒取物与归还（0.4.3）

从箱子中的潜影盒取货时，先将源盒暂借到一个空闲背包槽，通过 QuickShulker 打开，只取订单要求的物品及数量，然后把源盒放回同一容器当前可用的空槽，优先原槽。源盒不会作为订单货物交付；未请求的物品、盒子颜色和自定义名称保留。嵌套取物需要两个空闲非保护主背包槽（源盒和材料），空间不足但已有本单材料时先分批交付。

0.4.3 修复客户端未安装 QuickShulker 时，借出源盒后因缺少 `OpenShulkerPacket` 类而中断的问题。服务端提供该通道即可使用内置协议；客户端也安装 QuickShulker 时使用其已注册的协议，避免重复注册。取物后核对服务端源盒的预期剩余内容，等待客户端同步，再归还并重新开箱确认当前布局中的源盒内容。0.5.5 起原槽被占用时使用同一容器其他空槽；没有可用空槽时保留物品并停止。

## 执行异常立即停止（0.4.2）

普通订单开始前完全没有候选货源时，以 `failed / OUT_OF_STOCK` 结束。0.5.1 起取货过程中库存不足会交付已取物品，以 `partial_stored_offline` 结束，并通过普通聊天发送 `<物品ID> 缺货N个，已交付M个`。重复清单行共享库存，按物品 ID 汇总公告；不等待补货、不反复访问已确认无效的来源。`allowPartial` 保留兼容，不改变此行为。私聊与 HTTP 订单规则一致，发送者收到的 accepted 仅表示已入队。

背包无可用空槽、收货假人已满、转移或源盒内容核对失败、寻路或交互失败等异常仍立即结束本单并公告失败原因，释放队列；容器消失或借盒/转移前发现来源变化按 0.4.10 的候选切换处理。正常因背包容量不足进行的分批取货交付仍保留。已取物、借出的源盒、光标和在线假人留在原位；`needsItemReview=true` 提示核对，不自动回滚、不自动补发、不冻结后续订单。

## 安装

1. 使用 Minecraft 26.1.2、Java 25 或更新版本、Fabric Loader 0.19.5 或更新版本。
2. 将新版 `superwy-fabric-0.5.5.jar` 放入该游戏实例的 mods 目录，替换旧版机器人 jar，仅保留一个机器人版本；安装 Fabric API 0.155.3+26.1.2 或匹配的更新版。已有配置继续保留，Web 管理区域显示机器人实际版本。
3. 自动走路取货需要 Baritone API Fabric 1.18.0；嵌套源潜影盒需要服务端安装 QuickShulker Multi；机器人端已内置开盒协议，客户端 QuickShulker 可选。服务器还需 Carpet、GCA 的 `openFakePlayerInventory` 规则、`/player` 权限、方块及实体 NBT 查询权限。
4. 运行游戏，执行 `/superwy` 查看随机本机 Web 地址；游戏内 `/superwy token` 复制管理令牌后粘贴登录。

SQLite 驱动已经嵌入 mod，不需要额外运行 Node.js、数据库服务或 Web 前端构建工具。mod 严格声明支持 26.1.2；未测试的小版本没有放宽元数据。

切换同一机器人账号前，先停止旧 Node 机器人，避免其自动重连与新客户端互踢。

## 游戏私聊接单（0.4.0）

默认开启，不需要验证短 key。同服玩家可使用玩家取货端的 `/swrequest config` 配置后，通过 `/tell` 下单；不需要公网 HTTP/frp。接单机器人名是 `/tell` 的目标，收货假人名是稍后用于存放材料的假人，两者分别配置。

也可直接发送 `/tell WarehouseBot swget1 MyCargo minecraft:stone=64`，或用逗号合并物品清单。机器人识别原版私聊和系统包中的标准中英文私聊模板，公屏文字不会触发订单；订单进入原有持久 FIFO，保留原地交付、立即取消和 500 秒执行上限。

机器人游戏内执行 `/superwy whisper` 查看状态；`/superwy whisper on|off` 开关接单；`/superwy whisper key Ab123` 开启 5 位字母数字验证，`/superwy whisper key off` 关闭验证。配置立即保存，HTTP Bearer 验证不受影响。私聊订单可在 Web 管理列表查看和取消。

完整格式、回执、幂等和限制见 [私聊协议](PRIVATE_MESSAGES.md)。

## 首次设置

1. 对准选区第一个角的方块执行 /superwy pos1，再对准另一个角执行 /superwy pos2。
2. 执行 /superwy region warehouse 保存；也可以在游戏按键设置里绑定“两点选择仓库区域”。选择轮廓使用客户端粒子显示。
3. `/superwy scan` 或在 Web 点击“启动未停止区域”。检查扫描 complete、区块覆盖、外层及潜影盒内数量。
4. 快捷栏 0–8 可保留个人工具和食物；保护槽不参与取货。机器人只使用 9–35 中的空闲非保护槽，已有物品不会移动；有本单货物时按批次交付，无空槽可开始取货时立即失败，仍可接收新订单排队。
5. 在 Web 点击启用执行，或 `/superwy resume`，再提交清单与收货假人名称。初次安装默认不自动执行订单。

## 持久扫描、失败跳过与客户端黄标（0.2.1）

扫描队列保存在 `config/superwy/warehouse.db` 的 `scan` 文档中：待发现区块、待读容器、失败跳过位置和已完成计数均落盘。快照保存成功后才推进容器检查点；每一步写入完成后才执行下一步。

暂停、掉线、重启后，手动扫描或下一次定时任务会恢复未完成队列。容器或区块扫描失败后记录坐标与原因并持久跳过，不在本轮、下一轮定时扫描或重启后自动重试。正常暂停或掉线不算扫描失败，未完成的位置仍可恢复。扫描队列与失败记忆保留在检查点中，默认 3600 秒后开始新一轮扫描可用位置。修改区域世界、维度或边界会使旧检查点失效；删除区域会删除对应检查点，已有库存快照不重复累加。

如果在“快照已写入、检查点尚未提交”的瞬间断电，恢复时会安全重读这最后一个容器；不会漏扫或多算库存。手动接管规则见下文。

- 客户端给本轮**尚未处理且未被跳过**的已发现容器绘制黄色边框，128 格内绘制；成功读取或记录失败后移除。使用常规世界深度测试，与 Litestock 线框方式一致，不会显示被实心墙遮住的轮廓。
- HUD 显示待扫描数量、成功与跳过数量、最近 6 个容器坐标及未探索区块数；`/superwy unscanned <页>` 每页列出 10 个坐标。未知区块内的容器要等加载后才能发现，HUD 不会伪造位置。
- Web 管理 `scan.remainingContainers` 返回最近步骤所在区域的已发现待扫描坐标，各区域详见 `scanRegions`；客户端黄标合并当前世界各区域未处理坐标，`remainingChunks` 为待探索区块数，`skippedContainers`/`skippedChunks` 为跳过数量，`failures` 保留失败原因，`persistent=true` 表示已使用持久队列。暂停时保留黄标和待扫描列表，换世界或断线时清除当前显示，恢复扫描后重新显示。
- 玩家侧安装相邻项目 [SuperWY Requester](../superwy-requester/README.md)，可中键 Litematica 投影填写 1–64 个材料并向机器人下单，收货假人名称由玩家配置。

## 失败跳过与扫描期间下单

升级 0.2.1 后执行一次 `/superwy scan`，旧版 `partial` 的失败重试队列会转为跳过记录。例如原来剩余的 80 个失败容器，不会再当作未扫描位置反复尝试。已成功缓存的库存保留，无需删除数据库。

扫描结束允许带跳过项：`complete_with_skips` 表示本轮已经结束，不是卡住。`/superwy failed <页>` 查看本轮所在区域的失败坐标、原因；失败记录不参与可取库存。只有明确手动执行 `/superwy retry-failed <区域ID>` 才会清除该区域失败记忆并从头重扫；也可管理接口 `POST /api/v1/admin/scan/reset-failures` 提交 `{ "regionId": "warehouse" }`。操作前要结束取货和扫描任务。

执行器启用（`/superwy resume` 或 Web 启用执行）后，扫描期间可以正常通过 API、Web 或玩家取货端提交订单。库存已足够时，等当前单个扫描步骤结束就优先处理取货，HUD 显示“取货优先，扫描暂停”；取货完成继续原断点。开始前无候选货源的普通订单以 `failed / OUT_OF_STOCK` 结束；取货过程中缺货则交付已取物品并公告数量。扫描随后继续，不会等待扫描补货。

同一客户端的移动、开箱和交付由一个执行器管理，不同时争抢背包与寻路控制。

## 多人排队（0.3.0）

所有 API/Web/取货端请求共用队列，按**成功入队的先后顺序**处理。同一时刻只有一个订单执行移动、取物和交付；多个请求同时到达时由数据库事务决定先后，与客户端时钟无关。幂等重放不新增订单或排队位置。

- 每位玩家最多 5 个未结束订单，整个机器人最多 100 个；超限返回 429 / QUEUE_FULL。
- 排队位置包含正在处理的订单：第 1 位为队首，`ahead` 为前方未结束订单数。位置会随着交付完成、立即取消或超时结束向前移动。
- 队首取货过程中缺货时交付已取物品再结束；开始前无候选货源、机器人无空槽、普通订单收货假人满背包时失败并移出队列，按序尝试下一单。收货假人已在线时先清除再原地召唤。可由原请求玩家取消自己的订单；取消会立即停止本单并移出队列，物品、源盒和光标留在原位；有空闲槽且界面与光标就绪时继续下一单，不自动存入安全箱。
- 普通玩家只能查看/取消自己的订单。可以知道前方有几单，不能查看其他人的物品清单、假人名称或订单 ID。每人应使用不同 principalId 和令牌。
- 队列编号、未处理订单及重启后的顺序均保存在数据库。正在执行时重启会将本单记为失败，保留取货与操作证据，不重复投递；未开始订单保留 FIFO 顺序。
- 排队顺序按仓库、世界和维度计算；机器人必须连接订单绑定的世界/维度才会处理该单。

`POST /api/v1/orders`、查询及取消订单响应新增 `queueSequence` 和 `queue`：

```json
{"queueSequence": 42, "queue": {"sequence": 42, "position": 3, "ahead": 2, "totalPending": 5, "active": false}}
```

`GET /api/v1/queue?warehouseId=main`（orders:read）返回 `policy=fifo`、仓库总待处理数及自己的订单摘要，包括排队位置、等待原因和交付进度。机器人离线时仍返回已保存的订单。Web 订单列表也显示位置，并支持立即取消。详见 openapi.json。

## 已实现的流程

- 区域按世界、维度隔离，默认每小时刷新；扫描按区域独立控制并轮流推进，断线后不会当作空仓库。
- 遍历区块方块实体，仅扫描潜影盒、箱子、陷阱箱和木桶；未加载区块可由 Baritone 尝试巡查加载，失败后跳过；扫描结束为 complete 或 complete_with_skips。Servux 协议异常会另行暂停，保留待扫队列。
- 保存外层槽、潜影盒内部槽、数量、完整有效组件指纹。快照替换不重复累加库存。
- 储物箱、陷阱箱、木桶、放置潜影盒可作为货源；漏斗、熔炉等其他容器不扫描、不计入库存。末影箱、容器矿车和特殊模组容器不作为公共货源。
- 清单严格按行处理，同一行优先选择地面潜影盒、嵌套潜影盒、普通容器；同类来源按距离和缓存更新时间排序。
- 先检查已缓存且有效的库存，重复行共享需求；有候选即可逐箱核实，不等待整仓扫描完成；取货过程中候选耗尽后交付已取物品，通过普通聊天公告缺货和实际交付数量，不等待后台扫描补货。
- 源潜影盒借入背包工作槽、通过 QuickShulker 打开、精确取物、归还原外层容器当前可用空槽并核实，优先原槽；不会为取货把源盒放到世界中。
- 按缓存定位目标物品，优先地面放置潜影盒，其次潜影盒内物品和普通容器；接近后正常打开并核对槽位，支持 10 格交互和嵌套盒借读。
- 取齐材料后在机器人当前位置召唤请求指定假人，右键打开 GCA 背包，将散装物品放入 18–53 槽并核对 NBT 增量，确认后执行 kill 下线；空间不足时每批也在取货结束处交付。
- 物品同步错误、断线、手动接管、交付不确定时本单失败并保留证据，禁止自动重新投一份。
- Web 保留区域独立控制、扫描、清单下单、订单详情和暂停/启用；库存内容通过原有 API 按需查询，不在页面展示。

## 共享控制与后台寻路（0.3.4）

扫描和取货期间不锁键盘、鼠标、滚轮或聊天。玩家可以自由转向；按住方向键时按玩家镜头方向移动，保留 Baritone 的任务和目的地，松开后继续原路径。物理输入不会自动暂停、取消任务；按住方向键期间延后导航超时和卡住判断，松开后恢复正常超时保护。聊天中可正常执行 `/superwy stop`；`/superwy resume` 恢复执行。停止状态仍持久保存。

寻路临时使用 `freeLook=true`、`antiCheatCompatibility=false`、`blockFreeLook=true`、`smoothLook=false`，物理移动使用路径当前步骤的方向，镜头独立。结束时恢复原设置。任务运行时保持失焦后台执行；空闲恢复游戏原有失焦行为。

安装了旧 `baritone-steering-fix-0.1.0.jar` 时请替换为 **0.2.0**，否则旧补丁仍会强制转动镜头。新机器人检测独立补丁后让补丁统一处理移动，避免重复转换手动方向。

玩家实际修改交易中的物品或关闭交易界面仍可能导致交易校验失败，结束本单并保留核对记录以免重复取货。自由移动本身不会触发停止。

## 原地交付（0.3.8）

取齐本单材料后停止当前自动寻路，在机器人当前位置的精确 x/y/z 坐标召唤请求指定名称的假人，右键打开 GCA 背包并放入材料，核对后继续执行 `/player <名称> kill` 下线保存。背包不足导致分批交付时，每批都在取货结束的位置召唤，不返回固定平台。

接单和执行均不再要求交付站点。旧 `/superwy station box|recovery|delivery` 命令、配置及 `delivery.stationId` 字段保留兼容，但原地交付不读取这些坐标。Web 工作站表单改为原地交付说明，已有玩家取货端和脚本无需修改请求。

召唤坐标发送前持久保存到 `delivery.spawnPosition=[x,y,z]`，同时记录 `spawnMode=in_place` 和 `spawnDimension`。分批订单保存最近一批的召唤位置；收货核对仍使用实际 GCA 菜单及假人服务端库存。

## 立即取消与 500 秒强制超时（0.3.7）

网页或 `POST /api/v1/orders/{id}/cancel` 会立即停止本单寻路、等待、查询和后续取放动作。取消状态持久写入后返回 HTTP 200 / `cancelled`；不再返回“安全取消请求已提交”，也不等待物品归还、假人下线或进入恢复状态。排队订单直接移除，执行器随后处理下一单；没有下一单时本单自动移动停止。

普通任务从实际执行起最多运行 **500 秒**；0.5.0 的打包任务默认 **24 小时**。排队不计时，网络、寻路和交互耗时均计入。到时以 `failed / ORDER_TIMEOUT` 停止并释放队列。使用单调时钟，请求自身 `expiresAt` 仍生效，两者谁先到期谁先结束。

取消或超时不会自动归还源盒、移动剩余物品、清空鼠标光标、关闭交易界面或移除已召唤的收货假人；已经发给服务器的操作无法撤回。已核实的交付数量和物品台账保留，禁止为本单自动补发。下一单只使用新的空闲槽；0.5.3 起光标为空时自动关闭残留界面后执行，光标仍有物品则保留现场并停止，请先处理光标再下单。

订单响应新增 `executionStartedAt`、`executionStoppedAt`、`executionTimeoutSeconds=500`，中断时带 `terminationReason`（`USER_CANCELLED`、`ORDER_TIMEOUT`、`EXPIRED` 或 `EXECUTION_ERROR`）。取消和超时终态重启后保留，不会恢复执行。

## 背包与恢复

0.5.0 已恢复空盒领取与装箱，并新增交付后的全物品入口投放。取货使用 9–35 中的空闲非保护槽；完成后按新清理规则清空整个主背包 27 格。若取货或交付动作未核实，物品保留在原位，`needsItemReview=true` 提示核对。

升级启动时，旧版未结束的执行、等待、恢复订单一律记为失败并保留原错误及物品证据；未执行的 queued 订单仍按原顺序处理。已结束订单不会恢复执行。

## 按路径移动、跳跃与 10 格容器交互（0.3.2）

寻路期间，在实际移动向量计算时通过 Baritone 公共 `RotationMoveEvent` 取得当前移动步骤的 yaw，应用到物理移动，保留玩家镜头。独立补丁还会缓存提前清除前的目标，供移动与跳跃消费。这处理其他模组在 Baritone 普通转向钩子之后改写玩家 yaw 的情况，不以最终目的地替代当前路径步骤。前台、后台均适用，空闲或停止后不接管移动。

每次开始自动寻路先清除 Baritone 旧目标与残留的 `#pause`。临时开启 `allowParkour`、`allowParkourAscend`，关闭 `assumeStep`，允许实际起跳、上台阶和跨越空隙；仍禁止挖方块、放方块和搭桥。结束后恢复原设置。

到达判定使用 Baritone 的 `playerFeet` 与目标判定，兼容底半砖等实际站立高度。交付直接在取货结束时的机器人位置召唤假人，不再寻路到固定平台。

容器交互上限为眼睛到目标容器交互面的 **10 格**。0.3.6 起直接向缓存坐标发送开箱交互包，目标在头顶或被其他方块挡住时也允许原地尝试，不要求准星对准或可见射线。数据包使用原版递增交互序号并同步当前快捷栏选中槽，不转动镜头、不在客户端预执行物品使用。只有服务器实际打开容器菜单后才执行槽位操作。

服务端拒绝超距或遮挡交互时，等待超时后尝试按同步的交互距离靠近后重试一次，不附加客户端可见射线要求；箱盖被阻挡、权限或保护规则拒绝时仍不会视作成功。10 格是机器人尝试距离，最终可交互范围与开箱权限由服务器决定。

Web 管理区域和 `GET /api/v1/admin/status` 的 `navigation` 显示目标、实际位置、移动距离、转向应用次数、重规划次数与错误。连续 6 秒无进展且未在计算路径时重规划一次，14 秒仍无进展则返回 `NAVIGATION_NOT_MOVING`；总体寻路仍保留 30 秒上限。失败时同一份导航诊断写入日志，便于区分没有移动与走到了错误位置。

## 持久库存、每小时更新与关闭扫描（0.3.4）

容器最新成功快照（包含潜影盒内部物品、数量、槽位、组件与实际 `observedAt` 时间戳）和扫描进度保存在 `config/superwy/warehouse.db`。重启直接读取这些记录；不会用启动时间冒充扫描更新时间。重新扫描按容器键替换快照，数量不会重复累加。这里的历史记录指每个容器最后保存的快照，不是每次扫描的版本归档。

**库存没有时间过期限制。** 完整、可用的历史快照即使放置很久，仍计入可用量，也能用于取货；只因明确读取失败、来源变动等标记为不完整的快照才不再预留。取货时仍核对实际容器并更新正在操作的来源，避免把旧数量当作已成功取出。

默认每小时更新一次，按持久保存的本轮完成时间戳 + 3600 秒安排，支持包含跳过项的扫描结果。到期而机器人忙碌时排队等待；重启不会重新从启动时间计时。首次升级会把现有区域间隔迁移为 3600 秒，保留库存、原时间戳、扫描断点与失败记忆；此后仍可在区域设置中选择其他间隔。

- `/superwy scan off`：持久关闭定时、手动和缺货触发的全仓扫描，当前单步写入完成后停止；继续使用历史库存接单取货。在任务输入栏也可执行此命令，已有取货任务继续。
- `/superwy scan on`：重新开启扫描，未完成位置可续扫，到期区域安排更新。
- `/superwy scan`：开启扫描状态下，主动安排一次扫描。
- Web 扫描卡片的“关闭扫描，使用历史记录 / 开启扫描”按钮提供相同操作，并显示库存核实时间、下次定时扫描时间。
- 关闭扫描与“暂停执行”独立。`/superwy stop` 或 Web 暂停会停止取货；需要 `/superwy resume` 或 Web 启用执行恢复。恢复执行不会替你重新开启已关闭的扫描。

管理员接口：`POST /api/v1/admin/scan/disable`（`scan/stop` 为同义入口）和 `POST /api/v1/admin/scan/enable`，JSON 请求体 `{}`。开关写入 `config.json` 的 `scanEnabled`，重进服、重启仍保留。关闭时 `POST /admin/scan` 返回 409 `SCAN_DISABLED`。`capabilities` / 管理状态返回 `scanEnabled` 与 `inventoryMode`。

新订单被拒绝时，HTTP 503 返回具体就绪原因（例如 `AUTOMATION_DISABLED`、`OFFLINE`、`BARITONE_MISSING`），`error.message` 给出操作提示，`error.details.blockingReasons` 列出全部阻挡项。`CAPABILITY_UNAVAILABLE` 保留为无具体原因时的兜底，幂等重放已接受订单仍正常返回。关闭扫描本身不构成拒单原因。玩家取货端无需改队列逻辑即可看到新的具体错误码。

## 配置和数据

游戏实例下：

- config/superwy/config.json：管理令牌、玩家凭证、监听地址、工作槽和工作站。
- config/superwy/warehouse.db：库存快照、选区、订单、幂等键、操作台账；SQLite WAL。

默认监听 127.0.0.1。给其他玩家开放时，配置 bindAddress、allowedHosts，并通过受控的 HTTPS 反向代理提供地址。重启客户端后生效，游戏服务器仍需只给机器人相关权限。

在 credentials 数组中添加独立凭证，例如：

~~~json
{
  "principalId": "alice",
  "token": "替换为独立的长随机字符串",
  "fakePlayerNames": ["AliceDelivery"],
  "scopes": ["inventory:read", "orders:read", "orders:write"]
}


普通凭证只允许查看/取消本人的订单。手动配置及旧 swc1 凭证受获准假人名称约束；新 swc2 连接凭证设置 recipientSelectable=true，由取货端选择合法收货名。凭证至少 32 字符，主体 ID 和凭证均不得重复。管理令牌可以配置工作区和指定任意合法假人名，不应提供给其他玩家。

## API 与其他接入方式

浏览器中的“连接与接口”提供示例，GET /openapi.json 提供公共契约。核心路径：

| 方法 | 地址 | 作用 |
| --- | --- | --- |
| GET | /api/v1/capabilities | 执行能力、可接单状态、限额 |
| GET | /api/v1/inventory?warehouseId=main | 分页物品变体与数量 |
| POST | /api/v1/orders | 清单 + delivery.fakePlayerName + Idempotency-Key |
| GET | /api/v1/orders/{id} | 已取、已装、已交数量和异常 |
| POST | /api/v1/orders/{id}/cancel | 立即取消并持久保存 cancelled |

每请求最多 128 行，单行规范上限 10 亿，当前实现另有整单总量 100 万限制；每凭证最多 5 个未终结订单，写入每分钟 30 次。队列默认总上限 100。订单接收返回 202，幂等重放返回 200；同键改清单或假人名称返回 409。

也可用 Python 标准库客户端，示例清单在 examples/items.json：

~~~powershell
$env:SUPERWY_TOKEN = '你的独立接口凭证'
python tools/request_items.py --fake-player AliceDelivery --items examples/items.json --key bridge-20261025-001 --wait
~~~

网络重试沿用相同 --key；不要为同一次重试换新键。多批交付不能提供整单物理原子性，取消/过期后也会保留已核实的 delivered 数量。

## 恢复异常订单

1. 暂停执行，检查游标、本单背包货物、源盒原容器及目标假人。
2. 手工归还/存放确实属于该订单的物品，保留原有个人物品并清空游标；不需要清空全部主背包。
3. 核实本单物品去向后，由管理员调用 POST /api/v1/admin/orders/{id}/resolve，JSON 为 {"confirmation":"I_VERIFIED_ITEMS_AND_RECIPIENT"}。这会将订单标为 failed / MANUALLY_RECONCILED，不会抹去已经交付的数量，也不会重新发货。
4. 确认配置和物品实际位置后再启用执行。若需补单，按未交付的差额创建新订单。

目前不自动从半途物品事务恢复执行；只对尚未开始的 queued 订单安全续排，其他未终结状态在程序重启后要求核对。
